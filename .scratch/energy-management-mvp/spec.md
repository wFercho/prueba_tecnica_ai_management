# MVP de AI Energy Management: datos → análisis → decisión operativa

Status: ready-for-agent

## Problem Statement

Una persona que opera medidores eléctricos necesita saber qué ocurre, qué cambios se apartan del comportamiento esperado, cuáles requieren atención primero y por qué. La aplicación actual ya importa las lecturas, calcula anomalías y expone una API y una interfaz iniciales, pero todavía no ofrece de manera coherente todo el recorrido que el evaluador debe poder hacer delante de ella: entrar, examinar M-109 sin un diagnóstico precocinado, iniciar el análisis, ver cuatro episodios explicados con evidencia, investigar y decidir qué acción tomar. El arranque, la salud de los medidores, la confianza, la narración, el idioma visible y las vistas de resultados presentan discrepancias entre el comportamiento existente, las historias previas y el PDF original.

El PDF es la fuente de requisitos. Evalúa el resultado, no una librería ni una técnica de IA concreta. Sus dos rúbricas, la general y la específica de IA, suman 100 puntos cada una; los ejemplos ilustran el comportamiento esperado, no autorizan inventar datos ni consultar `expected_results.csv`.

## Solution

Ofrecer una demo local y reproducible de un producto de Energy Management. El evaluador levanta la aplicación, importa los CSV entregados, entra con una cuenta de demo, inspecciona lecturas y baseline sin resultados precomputados, ejecuta «Ejecutar análisis IA» y ve inmediatamente una tabla completa de episodios. Un detector determinista general decide el tipo, la severidad y el score de evidencia; las reglas siempre explican y recomiendan. Un LLM opcional puede mejorar la narración después, sin modificar la clasificación y sin impedir la demo offline.

Para el dataset entregado se esperan cuatro episodios: M-109 `REAL_ANOMALY/HIGH`, M-112 `DATA_QUALITY/HIGH`, M-104 `EXPLAINABLE/MEDIUM` y M-106 `FALSE_POSITIVE/LOW`; los otros ocho medidores no producen anomalías. M-109 encabeza la investigación, M-112 se valida como problema de calidad pese a un consumo estable y M-106 se muestra como decisión consciente de no escalar. El dashboard distingue salud de medidor, severidad de anomalía, confianza en la clase asignada y estado del análisis. Antes de analizar no afirma que haya cero anomalías ni que los medidores estén sanos.

La interfaz debe guiar Inicio de sesión → Panel general → M-109 → Ejecutar análisis IA → Anomalía → Explicación → Acción recomendada en 5–10 minutos. La acción es una propuesta, no un workflow de resolución. **Todo el texto visible de la aplicación estará en español**, incluidas razones, acciones, estados, errores, fechas y tooltips; los identificadores y valores originales de los CSV se preservan sin traducir en la fuente. El diseño de datos y las pruebas también deben sostener el comportamiento con otros CSV compatibles, no únicamente con IDs o fechas conocidos.

## Implementation Decisions

- **Fuente y alcance.** El PDF original prevalece frente a errores de su transcripción y frente a ejemplos tomados como contratos literales. En su tabla de medidores la última columna es «Anomalía», separada de «Estado»; M-112 es `ALERT/HIGH`. Sus ejemplos de confianza admiten `Media` o `Alta` para M-106; la distribución real se calcula, no se fija. Las librerías frontend y un límite de 60 segundos para construir imágenes no son requisitos del PDF.
- **Stack frontend elegido por el proyecto, no impuesto por el PDF.** Mantener React, TypeScript y Vite; incorporar Tailwind CSS 4 para estilos y tokens, TanStack Router para rutas tipadas y guard de navegación, TanStack Query para consultas, mutaciones, invalidación y polling, TanStack Table para filtros/ordenación de las tablas de medidores y anomalías, y Recharts como primera opción de gráficos. No añadir TanStack Start (el backend sigue en Go), TanStack Form para un único login ni TanStack Virtual para tablas pequeñas sin una necesidad demostrada. El cambio reemplaza la navegación local y el fetching manual actuales; no es una segunda implementación paralela.
- **Idioma de producto.** Todo el texto mostrado por la UI se redacta en español: login, navegación, KPIs, tablas, botones (incluido «Ejecutar análisis IA»), estados, validaciones, errores, unidades, leyendas, tooltips y acciones. Formatear fechas, horas y cantidades con una configuración española coherente y zona horaria identificable. Los identificadores (`M-109`), valores `status=OK` y enums de API se conservan como datos fuente, pero sus etiquetas visibles se traducen. Las plantillas deterministas y las instrucciones al LLM producen razón y recomendación en español; un fallo vuelve a las plantillas españolas, no al texto inglés. Los reportes de contexto entregados en inglés se explican en español en la UI sin sobrescribir su contenido original en almacenamiento.
- **Almacenamiento y arranque.** El modelo persistente incluye medidores, lecturas, reportes de contexto, runs, anomalías, usuarios y sesiones. El arranque crea solo la cuenta de demo ausente, con contraseña hasheada; una importación explícita reemplaza datos fuente y elimina resultados derivados sin tocar usuarios ni sesiones. El dataset queda sin anomalías y runs hasta que se pulse el botón. No se importa ni expone `expected_results.csv`.
- **Contratos de persistencia.** Extender el contrato de almacenamiento existente para provisionar/verificar usuarios, emitir y revocar sesiones, reiniciar fuente/resultados de forma transaccional y consultar separadamente el intento más reciente y el último run completado. Las implementaciones en memoria y PostgreSQL han de expresar el mismo comportamiento; la capa HTTP no consulta SQL directamente.
- **Límite de seguridad.** El backend valida usuarios almacenados en PostgreSQL; una cookie opaca HttpOnly identifica una sesión revocable en la base de datos. La API de datos y análisis requiere sesión; login y recursos públicos quedan accesibles sin ella. «Salir» revoca la sesión. API y puerto publicado de PostgreSQL se vinculan a localhost por defecto. `admin@email.com` / `admin` y las credenciales de BD por defecto son solo para la demo local, nunca una garantía de despliegue público. Más usuarios se provisionan administrativamente, sin gestión de cuentas en la UI.
- **Vocabulario.** Un reporte de contexto puede ser un evento operativo, un reporte de defecto o un reporte de ausencia de evento; `UNKNOWN` de M-109 no explica el episodio. El `status` ingerido de una lectura permanece verbatim y no es un veredicto de calidad. Un hallazgo de calidad es evidencia detallada, separada de los cuatro términos de confianza. La acción recomendada no ejecuta una transición humana; el único estado de anomalía soportado es `OPEN`, sin endpoint para reconocer, descartar o resolver.
- **Detector y baseline.** Siempre se ejecuta un detector determinista, general para CSV compatibles y sin condiciones por ID. Usa baseline propio por medidor, desviaciones frente a él, consistencia eléctrica y reportes de contexto. La evidencia eléctrica, no la etiqueta `DATA_QUALITY` del reporte, dispara M-112. Si falta historia fiable, se informa cobertura insuficiente sin asignar `HEALTHY` ni fabricar anomalía de consumo. Para el dataset entregado se esperan exactamente M-104 (96 lecturas), M-106 (12), M-109 (58) y M-112 (16), sin resultados en los ocho controles.
- **Episodios.** Una anomalía representa un episodio de un medidor, con límites horarios, contador de lecturas afectadas y origen de detección. Un episodio intermitente puede contener lecturas normales; el contador no las incluye. Hallazgos del mismo tipo separados como máximo tres horas pueden agruparse (umbral configurable); un hueco mayor los separa. Otros CSV pueden producir un número distinto de episodios.
- **Prioridad, salud y confianza.** Alta prioridad equivale a severidad `HIGH`, incluidos los episodios de calidad: dos en el dataset. La salud del medidor se obtiene del mayor impacto operativo de las anomalías vigentes del último run exitoso: M-109 `CRITICAL`, M-104/M-112 `ALERT`, M-106 `HEALTHY`. Antes del análisis o con datos insuficientes es desconocida. Confianza es un score reproducible [0,1] de evidencia de la **clase asignada** (también `FALSE_POSITIVE`), no una probabilidad ni una medida de urgencia. La API expone sus cuatro términos; la tabla muestra banda y el detalle explica el número. El dashboard muestra banda atribuida y distribución derivada, nunca media desnuda.
- **Detalle y visualización.** El consumo y el baseline comparados corresponden al mismo periodo; la última hora se muestra por separado. Antes de analizar, M-109 presenta lecturas y baseline sin banda ni etiqueta. Tras el run se ve la ventana del episodio. Prototipar primero el gráfico con Recharts y comprobar cuatro condiciones antes del resto del dashboard: banda distinta del baseline sin taparlo, tooltip en español con hora/real/baseline/desviación, eje legible por días a lo largo de 14 días y 58 horas de M-109 como bloque continuo. Si Recharts no satisface esas condiciones tras un spike acotado, usar SVG manual solo para ese gráfico y documentar la excepción. Distinguir series también por trazo/etiquetas, no solo color, y ofrecer resumen o tabla accesible de la evidencia. Voltaje, corriente y factor de potencia figuran en el detalle; metadatos inventados se etiquetan sintéticos.
- **Narración.** Las reglas persisten explicación y recomendación **en español** antes de responder. El LLM opcional solo reescribe **en español** a partir de identidad, límites, baseline, consumo y variables eléctricas por hora, desviaciones, reportes y hallazgos de calidad dentro del episodio; no recibe toda la historia ni puede alterar tipo, severidad o confianza. El resultado del proveedor se valida; una narración que no cumpla el contrato, incluido el idioma requerido, conserva las plantillas españolas. Sin key, las filas quedan `rules/READY`; con key pasan por `rules/PENDING` a `llm/READY` o conservan reglas como `rules/FAILED` si falla. La segunda pasada con LLM es opcional en la demo.
- **Run y HTTP.** `POST /ai/analyze` devuelve `202` y el identificador dentro de `run.id` solo después de detectar y persistir las anomalías con texto completo. `GET /ai/analysis/:id` expone `RUNNING → COMPLETED | FAILED`; `COMPLETED` solo significa detección terminada y el progreso de narración es por fila. La API de medidores, lecturas, anomalías y resumen mantiene sus rutas sugeridas por el PDF; el resultado de anomalía incluye `anomaly=true` como «episodio candidato», tipo, severidad, score, razón y acción. El último intento aporta fecha/estado; las vistas de hallazgos usan el último run completado y avisan cuando existe un intento posterior fallido. Las consultas de un medidor o episodio nunca mezclan anomalías históricas como si fueran actuales.
- **Experiencia de producto.** TanStack Router permite enlazar directamente a login, dashboard, medidor y anomalía sin depender de un estado local de pantalla; el guard de frontend mejora la navegación pero la API sigue siendo la frontera real de autenticación. TanStack Query posee el estado del servidor y detiene el polling cuando no quedan narraciones pendientes; TanStack Table ordena y filtra sin duplicar la lógica en cada vista. Los KPIs anteriores al primer run dicen «Pendiente de análisis», no cero; el resultado solo aparece tras pulsar el botón. El polling actualiza filas individualmente sin borrar sus explicaciones por reglas.
- **Documentación de entrega.** El README se actualiza durante la implementación para reflejar comandos reales, advertencia de credenciales conocidas, datos sintéticos, recorrido principal de 5–10 minutos y LLM opcional. El glosario y ADRs registran la separación entre salud/severidad, episodio, confianza, narración, login local y reset del seed; no se requiere crear un documento de persistencia ausente ni un ADR por cada librería.

## Testing Decisions

- Una buena prueba verifica **comportamiento observable** y datos de salida, no nombres de funciones privadas, una implementación concreta de gráfico, números mágicos de umbrales o texto LLM palabra por palabra. Debe fallar por un error que un operador/evaluador perciba: clasificación, prioridad, evidencia, autorización, historial o pantalla incoherente.
- **Seam principal existente: API HTTP + servicio.** Reutilizar pruebas con servidor HTTP en memoria, implementación de almacenamiento en memoria y narrador controlado. Probar login válido/inválido, cookie y protección de rutas, logout revocable, ausencia de resultados previa al run, `202` después de persistencia, tabla completa con reglas **en español**, transición por fila cuando el narrador responde/falla, repetición de runs y aviso de resultado anterior cuando falla el intento nuevo. Este seam permite inspeccionar JSON/códigos y la misma orquestación que usa el frontend sin una suite de mocks por capa.
- **Detector existente.** Reutilizar tests sobre los CSV entregados para los cuatro episodios y los ocho controles, y añadir contrafactuales con IDs/fechas cambiados, sin reporte de calidad de M-112, con fallos separados por más de tres horas, con datos insuficientes y con dos tipos de episodio en un medidor. No usar el ground truth reservado ni fijar la distribución de bandas del dashboard a un ejemplo.
- **PostgreSQL real existente.** Reservar integración SQL para aquello que el almacén en memoria no puede demostrar: migraciones idempotentes, hash/almacenamiento de usuarios, expiración y revocación de sesiones, atribución de anomalías a runs, reset transaccional de fuente/resultados con preservación de identidades, y consulta de último run exitoso frente a último intento fallido. Ejecutar contra BD descartable de tests, nunca borrar el volumen de la demo como parte de una prueba.
- **Contrato vivo y UI.** Adaptar el smoke de API vivo: autenticarse antes de consultar, comprobar rutas y campos que lee la UI, cuatro episodios, salud `ALERT/HIGH` de M-112, `OPEN` y ausencia del antiguo `PATCH` de workflow. Ejecutar el smoke en un entorno de prueba o tras la demo, nunca precorrer el análisis en la base destinada a mostrar el primer run. Validar visualmente el recorrido del navegador, enlaces directos y vuelta tras login, filtros/orden de TanStack Table, estados de Query, tooltip y banda del gráfico, accesibilidad por teclado, refresco de narraciones, logout e **idioma español en todas las vistas**. No introducir de entrada un nuevo framework E2E; añadirlo solo si estos seams dejan un hueco observable.
- La suite actual ya ofrece precedentes: tests table-driven del detector, tests HTTP sobre almacenamiento en memoria y narrador falso, tests SQL contra PostgreSQL descartable y un smoke del contrato API. Modificarlos donde sus expectativas reflejen el comportamiento antiguo, en vez de mantener tests contradictorios.

## Out of Scope

- ML local obligatorio, un LLM que decide tipo/severidad/confianza, o una API key obligatoria para la demo.
- Autenticación preparada para Internet, integración con un proveedor de identidad, registro público, administración de cuentas por UI o despliegue con `admin/admin`.
- Reconocer, descartar o resolver anomalías dentro de la app; `OPEN` es el único estado de revisión humana soportado.
- Enviar `expected_results.csv` al repositorio, a pruebas, a la aplicación, al detector o al LLM.
- Flag derivado en todas las lecturas, aunque sí se exponen hallazgos de calidad con horas y valores ofensores.
- TimescaleDB, ingestión en tiempo real, carga masiva o promesas de generalización perfecta ante distribuciones distintas.
- Sustituir el backend Go por TanStack Start, incorporar TanStack Form o Virtual sin necesidad, un kit de componentes obligatorio, un tiempo de build de 60 segundos, una banda adicional «Media-Alta» o frases literales de ejemplos del PDF. El stack de Router/Query/Table/Tailwind/Recharts sí es una decisión de este proyecto, aunque el PDF no lo exija.
- Contar como resultados actuales los runs anteriores o inventar un estado `HEALTHY` antes de analizar.

## Further Notes

- Esta spec describe el **objetivo**, no certifica que el código actual lo cumpla. Entre las diferencias conocidas están: importación por upsert que conserva resultados, ausencia de login, API `PATCH` de workflow no deseada, salud basada solo en severidad, KPI de alta prioridad que cuenta `MEDIUM`, distribución de confianza no mostrada, UI sin filtros/búsqueda/orden, gráfico sin tooltip y payload LLM que omite parte de la evidencia disponible. Los tickets deberán hacer esas diferencias explícitas y entregarlas sin prometerlas antes de tiempo en el README.
- El PDF original rotula «Anomalía» la última columna de §6; una transcripción Markdown la llama «Nivel». El PDF muestra M-112 `Alert/High`, por lo que salud y severidad no son la misma variable.
- `events.csv` contiene cuatro reportes, incluido `UNKNOWN` para M-109 («No operational event reported»). Para M-112 hay lecturas horarias con 16 lecturas defectuosas intermitentes cada tres horas; el `status=OK` del origen no las valida.
- Los resultados exactos 4/12 pertenecen al dataset entregado (4.032 lecturas, 336 por medidor). En datos compatibles distintos, los conteos pueden variar; la insuficiencia de historia se informa, no se disfraza de normalidad.
- Las historias de usuario detalladas y los ADRs aceptados son material de contexto para desglosar esta spec en tickets verticales. El flujo previsto es `to-spec` → `to-tickets` → `implement`; la implementación y la actualización del README ocurren en los tickets, no al publicar esta spec.
- Documentación técnica consultada para esta decisión: [Tailwind CSS 4 y Vite](https://tailwindcss.com/blog/tailwindcss-v4), [protección de rutas de TanStack Router](https://tanstack.com/router/latest/docs/framework/react/guide/authenticated-routes), [polling de TanStack Query](https://tanstack.com/query/latest/docs/framework/react/guides/polling), [filtrado/ordenación de TanStack Table](https://tanstack.com/table/latest/docs/framework/react/guide/column-filtering) y [ReferenceArea de Recharts](https://recharts.github.io/api/ReferenceArea).
